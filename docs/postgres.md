# Sprint 4.3 — PostgreSQL foundation

The migration in `supabase/migrations/20261127000100_crm_foundation.sql` is
a synthetic-only candidate for Supabase PostgreSQL. It does not create a cloud
project, expose an API schema, connect the local dashboard, or accept real
customer records.

## Data and permissions

- `genyx_crm.members`: approved Supabase Auth user IDs and operator/viewer roles.
  Membership changes require the database owner.
- `genyx_crm.leads`: owner-scoped synthetic request ID, service, locale,
  timeline, derived priority, stage, and server timestamps.
- `genyx_crm.lead_events`: append-only application history generated by triggers.

Authenticated operators can insert and advance only their own records. Viewers
can read their own assigned records. Unapproved identities cannot access rows.
The anonymous and service roles are denied schema usage. The database owner
remains privileged. Keep the schema out of Supabase's exposed API schemas.
No client keys or database passwords belong in the public application.

Stage transitions match the existing SQLite domain. Terminal records cannot
be advanced. Request IDs are unique per owner; duplicate submissions fail
with a unique violation on direct insertion. The later ingestion function
handles exact replays; see [n8n PostgreSQL bridge](n8n-postgres.md).
No user can update ownership, membership, priority, or audit rows through
the granted application privileges.

## Local verification

Start Docker Desktop and run:

```powershell
npm run test:postgres
```

The script launches an isolated PostgreSQL 17 container without network access
or published ports, applies a test-only Auth role/function shim, applies the
migration, executes authorization and history assertions, then removes its
container and anonymous volume. It never uses a remote database URL. A first
run may download the official PostgreSQL image. The major image tag is not
digest-pinned; pin the tested image before adopting it as a release artifact.

The plain PostgreSQL tests exercise SQL grants, constraints, RLS and triggers,
not Supabase Auth JWT validation or the Supabase Data API. Do not run the
bootstrap or test fixtures on a hosted project.

## Before hosted deployment

- Choose and approve a separate development Supabase project and its region.
- Validate the migration in that project's actual Supabase environment.
- Keep `genyx_crm` private; approve a separate authenticated access design.
- Provision members through a privileged administrative operation, not signup.
- Decide retention, deletion, backups, and the production identity workflow.
- Add a server-side adapter and verify real authentication, failure handling,
  and isolation before any commercial ingestion.

The local SQLite dashboard and n8n test bridge remain unchanged. No real
contact information or customer-data transfer is permitted in this sprint.
