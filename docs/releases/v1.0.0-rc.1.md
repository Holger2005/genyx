# GENYX 1.0.0-rc.1 — Launch candidate

Status: proposed technical release candidate. Not the stable 1.0.0 release,
not a live deployment, and not authorization to accept actual customer data.

## Scope

- Bilingual public website, six services, one first-party prototype case,
  optional contact links, local inquiry draft, and empty SaaS catalog.
- Private loopback dashboard, synthetic SQLite and n8n laboratory, candidate
  PostgreSQL migrations and tested authorization model.
- Static export with preview-only headers, security checks, localized social
  metadata, and commercial planning tools.

The package, root lockfile and site version are aligned. Dependency versions
and lockfile resolutions are unchanged.

## Technical acceptance

```powershell
npm ci
npm run check
npm run test:sales
npm run test:postgres
npm run build:static
npm run test:static
```

CI additionally runs the existing boundary, security, admin, bridge, browser,
SEO and Lighthouse checks. The local static HTTP smoke checks every localized
page, representative forbidden routes, POST rejection, baseline headers and
the exported JS/CSS/SVG files. It does not emulate all Cloudflare behavior.
The SHA-256 manifest is written outside out; only out is a public deployment
candidate. The manifest identifies bytes, not the authenticity of an artifact
by itself. CI uploads separate short-lived preview and manifest artifacts.
Verify fresh checks on the exact candidate before any merge or promotion.

## Commercial website launch gates

- [ ] Approve hosting terms and public contact identity; verify business
      registration, invoicing and applicable tax requirements.
- [ ] Verify authorized Calendar/WhatsApp links and portfolio publication rights.
- [ ] Approve the applicable privacy notice, rights channel and provider handling.
- [ ] Provision an approved hosting project and verify HTTPS, routing, headers,
      custom domain if desired, and rollback using an approved artifact.
- [ ] Approve canonical URLs, hreflang, sitemap and indexing separately.
- [ ] Obtain explicit owner approval for commercial publication.

## Separate real-data backend gates

- [ ] Provision and test actual Supabase with managed identity and MFA.
- [ ] Implement the private production adapter and validate RLS with real Auth.
- [ ] Approve retention, deletion, incident response, abuse protection and backups.
- [ ] Verify production n8n credentials, failure recovery and authenticated intake.
- [ ] Obtain explicit approval before processing real personal data.

The public read-only website may be reviewed independently of the private
backend. Keep the laboratory synthetic and noindex enabled until the relevant
approval gates are met. Do not promote this candidate to stable 1.0.0 merely
because all automated tests pass.
